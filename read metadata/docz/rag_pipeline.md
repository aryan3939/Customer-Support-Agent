# RAG Pipeline Documentation

This document describes the current Retrieval-Augmented Generation (RAG) pipeline implemented in this repository. It is based on the code in `src/`, the database setup in `scripts/setup_db.py`, and the libraries listed in `requirements.txt`.

## 1. Goal

The system answers questions about OpenMetadata documentation by:

1. ingesting documentation pages into a searchable knowledge base,
2. converting cleaned documentation chunks into embeddings,
3. storing both text and vectors in PostgreSQL/Supabase,
4. retrieving relevant context with hybrid search, and
5. generating grounded answers through a LangGraph-based agent loop.

This is not a plain single-step RAG chain. The runtime path is agentic: retrieve, grade, optionally rewrite the query, then generate.

## 2. Dependency Map From `requirements.txt`

The RAG pipeline depends mainly on the following packages:

- `crawl4ai`, `httpx`, `lxml`
  Used for sitemap discovery, browser-based scraping, and document parsing.
- `langchain`, `langchain-core`, `langchain-community`, `langchain-openai`
  Used for prompts, messages, model wrappers, and general LLM integration.
- `langchain-text-splitters`
  Used for the two-stage chunking pipeline.
- `langgraph`
  Used to build the stateful agent graph for retrieval, grading, rewriting, and generation.
- `sentence-transformers`
  Used for local embeddings with `all-MiniLM-L6-v2`.
- `supabase`, `psycopg2-binary`
  Used for storage, RPC access, and schema setup on PostgreSQL + pgvector.
- `openai`
  Used as an OpenAI-compatible client layer for providers such as Groq, OpenRouter, and Modal.
- `langsmith`
  Optional tracing and observability for runs.
- `rich`
  CLI output and logging.

The evaluation-related packages (`ragas`, `datasets`, `tabulate`) are intentionally not the focus of this document.

## 3. End-to-End Flow

The full RAG pipeline has two phases: offline ingestion and online query answering.

### 3.1 Offline Ingestion

1. Fetch sitemap URLs from OpenMetadata docs.
2. Filter URLs by target version and allowed documentation categories.
3. Scrape each page with Crawl4AI using a browser-rendered Markdown output.
4. Clean the Markdown by removing navigation noise and Mintlify artifacts.
5. Chunk each page using a two-stage Markdown-aware chunker.
6. Generate embeddings for every chunk.
7. Upsert the source page and store all chunk records in Supabase/PostgreSQL.
8. Build retrieval-ready indexes and query functions in PostgreSQL.

### 3.2 Online Query Answering

1. Route the query.
2. If it is a greeting or meta question, answer directly.
3. Otherwise run hybrid retrieval:
   - vector similarity search,
   - parent-context expansion for vector hits,
   - keyword full-text search,
   - reciprocal-rank fusion.
4. Grade retrieved documents for relevance with the LLM.
5. If no relevant documents remain, rewrite the query and retry.
6. Generate the final answer strictly from retrieved context.

## 4. Ingestion Layer

### 4.1 Sitemap Discovery

`src/ingestion/sitemap_parser.py` fetches the sitemap and filters it using:

- `IngestionConfig.DOCS_VERSION = "v1.12.x"`
- `IngestionConfig.CATEGORIES`
- `IngestionConfig.MAX_PAGES = 1000`

It also removes low-value CRUD-style leaf pages with a suffix filter. This keeps the knowledge base closer to user-facing documentation and away from noisy autogenerated subpages.

### 4.2 Scraping

`src/ingestion/scraper.py` uses `AsyncWebCrawler` from Crawl4AI. This matters because the OpenMetadata docs are Mintlify-based and heavily client-rendered. A plain `requests + BeautifulSoup` approach would miss much of the real content.

The scraper:

- bypasses cache,
- excludes `nav`, `footer`, and `header`,
- removes overlay elements, and
- extracts Markdown instead of raw HTML.

### 4.3 Cleaning

Before chunking, the scraper cleans the page body by:

- trimming content between `"On this page"` and `"Was this page helpful?"`,
- removing Mintlify-generated empty links like `[](url#section)`,
- removing empty headings and stray numbered lines,
- collapsing repeated blank lines.

This cleaning step is important because bad boilerplate becomes bad chunks, and bad chunks become noisy retrieval results.

## 5. Chunking Strategy

The current chunker in `src/ingestion/chunker.py` is a two-stage structure-aware chunker.

### 5.1 Stage 1: Header-Based Splitting

The first pass uses `MarkdownHeaderTextSplitter` and splits on:

- `##` -> `h2`
- `###` -> `h3`
- `####` -> `h4`

This preserves documentation structure and attaches section metadata to each chunk.

### 5.2 Stage 2: Recursive Splitting

If a section is still too large, the second pass uses `RecursiveCharacterTextSplitter` with:

- `ChunkingConfig.CHUNK_SIZE = 1500`
- `ChunkingConfig.CHUNK_OVERLAP = 300`

Separators are ordered from stronger structure to weaker structure:

- paragraph breaks,
- line breaks,
- sentence boundaries,
- words,
- characters.

### 5.3 Why This Chunking Was Chosen

This chunking design improves RAG quality because:

- chunks do not arbitrarily cross major section boundaries,
- small sections remain intact,
- oversized sections are still split safely,
- sub-chunks inherit heading context,
- the embedding model sees both local content and section intent.

Each stored chunk includes metadata such as:

- `source_url`
- `source_title`
- `section_heading`
- `chunk_index`
- `total_chunks`
- heading lineage like `h2`, `h3`, `h4`

## 6. Embedding Layer

`src/embeddings/embedding_service.py` wraps `SentenceTransformer` as a singleton so the model loads once and is reused.

Current embedding configuration:

- model: `all-MiniLM-L6-v2`
- dimensions: `384`
- device: `cpu`

Why this works well for the project:

- local and free,
- fast enough for ingestion and query-time embedding,
- small vector size for efficient pgvector storage,
- strong baseline quality for technical-document retrieval.

## 7. Storage Layer

The storage backend is Supabase/PostgreSQL with `pgvector`.

### 7.1 Tables

The core tables are:

- `sources`
  Stores page-level metadata such as URL, title, category, hash, and raw content.
- `documents`
  Stores chunk text, embedding vector, chunk order, and metadata.

Conversation tables (`conversations`, `messages`) also exist, but they are not the core of the retrieval pipeline.

### 7.2 Indexes

The retrieval path depends on:

- HNSW vector index on `documents.embedding`
- GIN full-text index on `to_tsvector('english', content)`
- supporting indexes on source/category/chunk ordering

This lets the system serve both semantic retrieval and exact-term lookup efficiently.

### 7.3 Database RPC Functions

The database exposes three important RPCs:

- `match_documents`
  Semantic search with cosine similarity.
- `keyword_search`
  Full-text search using `websearch_to_tsquery`.
- `get_surrounding_chunks`
  Fetches neighboring chunks for parent-context expansion.

## 8. Retrieval Layer

The live retrieval logic is implemented in `src/agent/nodes.py`.

### 8.1 Query Routing

`route_query` first checks whether the user message is just a greeting, help prompt, or meta question. If yes, the graph skips RAG and answers directly.

### 8.2 Hybrid Retrieval

If the query needs documentation lookup, `retrieve` performs hybrid retrieval:

1. embed the query,
2. run vector similarity search through `match_documents`,
3. expand vector hits to parent context using surrounding chunks,
4. run keyword search through `keyword_search`,
5. fuse both result lists using reciprocal-rank fusion (RRF),
6. return top-k merged documents.

Current retrieval settings:

- `TOP_K = 5`
- `SIMILARITY_THRESHOLD = 0.5`
- `EXPAND_CONTEXT = True`
- `CONTEXT_WINDOW = 1`

### 8.3 Small-to-Big Retrieval

The retrieval path is effectively small-to-big:

- search happens against chunk-level units,
- then top vector hits are expanded to include surrounding chunks,
- final generation sees richer context blocks instead of only tiny fragments.

This keeps retrieval precise while giving generation enough context to answer well.

### 8.4 Reciprocal-Rank Fusion

Vector and keyword results are merged using reciprocal-rank fusion.

Why this is useful:

- vector search handles paraphrases and semantic similarity,
- keyword search handles exact connector names, config keys, product terms, and literal matches,
- fusion avoids overcommitting to either dense-only or sparse-only retrieval.

## 9. Agentic Control Flow

The query-time orchestration lives in `src/agent/graph.py` and `src/agent/nodes.py`.

The graph currently has these major nodes:

- `retrieve`
- `grade_documents`
- `rewrite_query`
- `generate`
- `generate_direct`

### 9.1 Grade Step

After retrieval, each document is checked with a binary relevance grader prompt. This step filters out retrieval noise before answer generation.

### 9.2 Rewrite Step

If grading removes all retrieved documents and the retry budget allows it, the agent rewrites the query and loops back to retrieval.

Current rewrite limit:

- `REWRITE_MAX_ATTEMPTS = 2`

### 9.3 Generate Step

The final answer is generated only from the retrieved context block. The system prompt instructs the model to:

- answer only from context,
- cite sources,
- stay on OpenMetadata-related topics,
- say it does not know if the context is insufficient.

This is the grounding layer of the pipeline.

## 10. LLM Layer

The project uses `ChatOpenAI` as the OpenAI-compatible wrapper, but the active backend is configurable.

Current config in `src/config.py`:

- provider: `groq`
- model: `llama-3.3-70b-versatile`
- base URL: `https://api.groq.com/openai/v1`
- temperature: `0.3`
- max tokens: `1024`

The `Secrets.llm_api_key()` method selects the right API key based on the active provider.

## 11. Why This Pipeline Fits Documentation QA

This architecture works well for documentation RAG because:

- the source content is structured and heading-heavy,
- exact terminology matters,
- long pages need chunk-aware retrieval,
- many user queries are paraphrased or underspecified,
- false positives are common without grading,
- a second retrieval attempt often rescues weak first-pass queries.

In short, the system is optimized for technical documentation rather than generic web QA.

## 12. What Is Verified Right Now

At the code level, the following checks are safe and currently useful as sanity checks:

- Python compilation across `src/`, `eval/`, and `scripts/`
- local chunker behavior with `scripts/test_chunker.py`
- artifact cleaning behavior with `scripts/regex_test.py`

Network-dependent verification such as live scraping, database RPC calls, provider APIs, and end-to-end online evaluation still depends on configured credentials, local model cache state, and outbound connectivity.

## 13. Current RAG Summary

The repository currently implements:

- browser-based documentation ingestion,
- deterministic Markdown cleaning,
- two-stage structure-aware chunking,
- local sentence-transformer embeddings,
- pgvector semantic search,
- PostgreSQL full-text keyword search,
- parent-context expansion,
- hybrid rank fusion,
- document grading,
- query rewriting,
- grounded answer generation with citations.

That combination makes the pipeline a production-style agentic RAG system rather than a basic retrieve-and-answer demo.
